=== STEP 2: IDENTIFY THE OVERCOUNTING ===

The gap is 16 Meta leads vs 4 CSV emails.
This means the Lead event is firing
without a real form submission occurring.

Check for these specific bugs:

BUG A — Lead firing on page load:
Search for fbq('track', 'Lead') that is
NOT inside a form submit handler.
Any Lead event outside an addEventListener
or form submit = firing on every page load.

BUG B — Lead firing for returning users:
If the gate checks localStorage and the
user already has access, the Lead event
must NOT fire again.
Check if the returning user path fires Lead.

BUG C — Lead firing on gate dismiss:
If user closes the gate without submitting,
Lead must NOT fire.
Check if any close/dismiss handler fires Lead.

BUG D — Lead firing on page load 
if mora_access localStorage is already set:
The gate hides itself but if Lead fires
before checking localStorage it counts
every page load as a lead.

BUG E — Server-side Lead firing without
a matching browser submission:
Check if track_lead() in meta_pixel.py
is being called from any route other
than /api/gate-signup.

BUG F — Lead firing twice per submission:
One browser fire + one server-side fire
without proper event_id deduplication.
If event_ids don't match Meta counts both
as separate leads.

=== STEP 3: THE CORRECT FIRING LOGIC ===

The Lead event must fire EXACTLY ONCE
per unique email submission.

CORRECT flow:
1. User visits site — NO Lead event
2. User sees gate — NO Lead event
3. Returning user (localStorage set) — 
   gate hidden immediately, NO Lead event
4. User types email and clicks submit
5. POST /api/gate-signup called
6. Server saves email to CSV
7. Server fires server-side Lead via
   Conversions API with unique event_id
8. Server returns event_id in response
9. Browser fires fbq('track', 'Lead')
   with SAME event_id for deduplication
10. Meta deduplicates and counts ONE lead

INCORRECT flows to eliminate:
- fbq Lead on page load = counts visits
- fbq Lead on gate view = counts impressions
- fbq Lead on returning user = counts
  every repeat visit
- fbq Lead without event_id = double counts
  with server-side

--- FIX E: Browser checks for event_id
before firing ---

The browser should only fire the Lead
pixel if data.event_id is present.
Returning users get no event_id.

Update the browser fire to:

if (data.success) {
  // Only fire pixel if server confirmed
  // this is a new email (event_id present)
  if (data.event_id) {
    try {
      if (typeof fbq !== 'undefined') {
        fbq('track', 'Lead', {
          content_name:     'Mora Bets Free Access',
          content_category: 'Sports Betting Tool',
          value:            14.99,
          currency:         'USD'
        }, {
          eventID: data.event_id
        });
      }
    } catch(e) {}
  }

  localStorage.setItem('mora_access', '1');
  localStorage.setItem('mora_email', email);
  // animate gate out
}

This is the critical fix. If event_id
is missing (returning user) the browser
pixel never fires. Only new emails
trigger the Lead event.
